Relationships: There are no strict foreign key constraints — the schema uses logical references (dotted line) instead of enforced FKs. This keeps SQLite simple and lets rows survive if a source or rule is deleted. Orphaned rows are surfaced as warnings in the UI.

3. Table: publications

The core table — every collected or manually added document.

ColumnTypeNullablePurpose
idIntegerNoPrimary key
titleStringNoPublication title
institutionString (indexed)NoBIS / IMF / World Bank / CBK / custom
source_urlStringNoLink to original — never overwritten (traceability)
published_dateDateTime (indexed)YesWhen the source published it
document_typeStringYespress_release / speech / working_paper / …
abstractTextYesShort summary from the source
raw_contentTextYesFull text (when available)
fingerprintString (UNIQUE, indexed)NoSHA-256 of institution|source_url|title — duplicate detection
ai_summaryTextYes6-section AI summary from Ollama
ai_topicsStringYesComma-separated topic slugs
ai_relevanceTextYesBOT relevance note + disclaimer
ai_processedBooleanNoHas the AI pipeline run?
ai_processed_atDateTimeYesWhen AI last ran
ai_engineStringYesollama or rule-based
hiddenBoolean (indexed)NoExcluded from analyst views (admin can hide)
manualBooleanNoAdded manually vs. collected
collected_atDateTimeNoWhen the system stored it

Design notes

  • Fingerprint is UNIQUE at the DB level — even if code has a bug, the database rejects duplicates.
  • AI columns are nullable — a publication is stored first, enriched second.
  • hidden replaces delete — nothing is ever lost; admins can restore.
  • Indexes: institution, published_date, fingerprint, hidden.

5. Table: alert_rules

User-defined watch rules for notifications.

ColumnTypePurpose
idIntegerPrimary key
keywordStringText to match (case-insensitive)
sourceStringall or specific institution
topicStringall or specific topic slug
priorityStringhigh / medium / low
created_byStringUsername
created_atDateTime
activeBooleanDisable without deleting

Matching rules (all must be true)

  1. Rule source is all, OR equals the publication's institution
  2. Rule topic is all, OR is in the publication's ai_topics
  3. Rule keyword appears in title, abstract, ai_summary, or ai_topics

6. Table: rule_matches

Records every match between a rule and a publication.

ColumnTypePurpose
idIntegerPrimary key
rule_idInteger (indexed)References alert_rules.id
publication_idInteger (indexed)References publications.id
matched_atDateTimeWhen the match was created

8. Users

Users are stored in memory in backend/app/users.py, not in the database. This is intentional for the prototype:

  • No password hashing (prototype only — documented)
  • Resets when the backend restarts
  • Upgrade path: add a users table with hashed passwords

9. Known Limitations

LimitationImpactFix if needed
No users tableLogins reset on restartAdd User model + hashed passwords

No FK constraint on rule_matchesOrphan rows possibleAdd ON DELETE CASCADE
No UNIQUE on (rule_id, publication_id)Theoretical duplicate matchesAdd UNIQUE constraint
Plain-text password (in-memory)Security risk if compromisedUse bcrypt/argon2
No migrationsALTER TABLE done manuallyAdd Alembic

10. Example Queries

Count publications by source

SELECT institution, COUNT(*) FROM publications
WHERE hidden = 0
GROUP BY institution
ORDER BY COUNT(*) DESC;

Find fallback rows that need reprocessing

SELECT id, title FROM publications
WHERE ai_engine = 'rule-based' AND hidden = 0;

Recent rule matches

SELECT r.keyword, p.title, m.matched_at
FROM rule_matches m
JOIN alert_rules r ON r.id = m.rule_id
JOIN publications p ON p.id = m.publication_id
ORDER BY m.matched_at DESC
LIMIT 10;

Orphaned publications

SELECT institution, COUNT(*) FROM publications
WHERE institution NOT IN ('BIS', 'IMF', 'World Bank', 'CBK')
  AND institution NOT IN (SELECT name FROM sources)
GROUP BY institution;
